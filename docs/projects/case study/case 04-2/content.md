# TL;DR

## Background

새로운 접근성 기능을 TV 제품에 적용하기 전, 실제 접근성 사용자가 기능을 이해하고 사용할 수 있는지 검증해야 했어요.

## Problem

기능 자체는 준비되어 있었지만, 사용자가 설정 과정에서 어디서 막히는지, 어떤 문구를 오해하는지, 어떤 피드백이 부족한지는 아직 명확하지 않았습니다.

## Approach

전맹 4명, 저시력 4명, 청각장애 3명까지 총 11명의 접근성 사용자를 대상으로 Task 기반 UT와 심층 인터뷰를 진행했습니다. 행동 로그, VOC, 5점 척도 정량 평가를 함께 분석해 사용 흐름별 병목을 구조화했어요.

## Result

사용자가 기능을 이해하고 수용하는 지점과 이탈 가능성이 높은 지점을 구분했습니다. 이를 바탕으로 제품팀이 우선 개선해야 할 UX 이슈를 정의하고, Interaction, UX Writing, Information Architecture 개선 방향을 Product Recommendation으로 정리했습니다.

# Key Metrics

## 11 Accessibility Users

실제 사용 맥락에서 검증했어요.

전맹, 저시력, 청각장애 사용자까지 총 11명을 대상으로 접근성 기능의 이해도, 유용성, 만족도, 향후 이용 의향을 검증했습니다.

---

## Task-based UT

의견이 아니라 행동을 봤어요.

사용자가 기능을 찾고, 이해하고, 설정하고, 다시 조정하는 흐름을 Task 단위로 관찰했습니다. 단순 선호도가 아니라 실제 조작 과정에서 발생하는 혼란과 병목을 확인했습니다.

---

## Quant + VOC Analysis

숫자와 말이 같은 문제를 가리키는지 확인했어요.

5점 척도 평가와 인터뷰 VOC를 함께 분석했습니다. 예를 들어 일부 기능은 이용 의향이 높았지만, 진행 피드백과 조작 효율성은 상대적으로 낮게 나타나 개선 우선순위로 분리했습니다.

---

## Product Recommendation

문제를 발견하는 데서 끝내지 않았어요.

발견된 이슈를 Interaction, UX Writing, IA 개선 방향으로 정리했습니다. 제품팀이 다음 단계에서 바로 논의할 수 있도록 우선순위 기반의 개선 제안으로 연결했습니다.

# Background

## 접근성 기능은 정말 쓸 수 있는지 검증하는게 더 중요했어요

팀은 TV에 적용될 새로운 접근성 기능을 출시 전 검증하는 단계에서 시작됐어요.

기능의 방향은 이미 정해져 있었지만, 제품팀에게 더 중요한 질문은 따로 있었어요.

“실제 접근성 사용자가 이 기능을 스스로 이해하고 사용할 수 있을까?”

접근성 기능은 단순히 기능을 제공했다고 끝나는 영역이 아닙니다. 사용자가 메뉴를 찾고, 문구를 이해하고, 설정값을 조정하고, 적용 여부를 확인할 수 있어야 실제 제품 경험이 됩니다.

그래서 이번 프로젝트는 기능의 필요성을 확인하는 것보다, 기능이 실제 사용 흐름 안에서 이해 가능하고 조작 가능한지 검증하는 것에 집중했어요.

# Problem

## 사용자는 ‘지금 제대로 되고 있는지’를 먼저 확인 받고 싶어 했다

실제 UT 과정에서는 우리가 예상하지 못한 문제가 더 중요했어요.

기능이 좋아 보여도, 사용자가 설정 문구를 이해하지 못하거나, 변경 결과를 바로 확인하지 못하거나, 메뉴 구조가 한 단계 더 깊어지는 순간 사용성은 크게 떨어졌어요.

특히 접근성 사용자는 일반 사용자보다 피드백 지연, 복잡한 문구, 불명확한 상태 변화에 더 민감했어요.

그래서 제품팀이 집중해야할 문제를 ‘신기능 평가 중심’에서 ‘사용자가 기능을 이해하고, 설정하고, 다시 조정하는 흐름 중 어디에서 멈추는가?’로 바꿔 집중하기로 했어요.

# What I Did

## 사용자 행동을 제품 개선 우선순위로 바꾸다

11명의 접근성 사용자를 대상으로 Task 기반 UT를 진행했습니다.

각 Task에서는 사용자가 기능을 처음 마주했을 때의 반응, 설정 과정, 세부 조정, 재사용 의향을 함께 확인했어요.

분석 과정에서는 단순히 긍정/부정 의견을 나누는게 아니라 행동 로그와 정량 평가, VOC를 함께 보면서 문제를 세 가지 기준으로 정리했어요.

1. 사용자가 기능의 목적을 이해하는가.

2. 사용자가 원하는 설정까지 도달할 수 있는가.

3. 설정 변경 후 결과를 즉시 확인할 수 있는가.

이 기준을 바탕으로 제품팀이 먼저 해결해야 할 UX 이슈를 우선순위화하고, Interaction, UX Writing, Information Architecture 관점의 개선 방향으로 정리했습니다.

# Key Findings

## 기능 수용도는 높았지만, 사용 흐름에서 개선점이 드러났어요

사용자들은 접근성 기능 자체에는 대체로 긍정적이었어요.

실제 평가에서도 일부 항목은 4.5점 이상으로 높게 나타났고, 향후 이용 의향도 긍정적으로 확인됐어요.

하지만 사용 흐름을 자세히 보면 개선해야할 지점이 명확했어요.

- 설정 변경 결과를 즉시 확인하기 어렵거나,
- 문구가 길고 낯설거나,
- 메뉴 구조가 추가되는 경우에 사용자가 부담을 느꼈어요.

정량 평가에서도 진행 상황 피드백과 조작 효율성은 상대적으로 낮은 점수로 나타나 우선 개선 영역으로 분류했어요.

즉, 핵심은 설정의 결과를 사용자가 예측하고 통제할 수 있는 구조를 더 명확히 하는 것이었어요.

# Design Direction

## 제품팀이 바로 고칠 수 있는 디자인 단위로 정리했어요

실제 화면과 기능명은 공개할 수 없지만, 개선 방향을 크게 세 가지로 정리할 수 있습니다.

### 1. 상태 피드백을 더 빠르게 전달하기

설정값을 변경한 직후 사용자가 결과를 바로 알 수 있도록 실시간 피드백 구조를 강화해야 했습니다.

### 2. 문구를 짧고 명확하게 바꾸기

접근성 사용자는 긴 설명보다 핵심 상태와 다음 행동을 빠르게 이해할 수 있는 문구를 선호했어요.

### 3. 설정 구조를 한눈에 파악 가능하게 만들기

메뉴 뎁스를 늘리기보다, 사용자가 어떤 기능을 조정하고 있는지 현재 위치와 상위-하위 관계를 쉽게 알 수 있어야 했어요.

# Outcome

## 사용성 평가로 제품 개선 우선순위를 분명히 했어요

이번 프로젝트 결과는 UT 리포트가 아니였습니다.

11명 사용자 검증을 통해 기능의 수용 가능성과 사용 흐름 병목을 함께 확인했고, 정량 평가와 VOC를 근거로 제품팀이 우선 개선해야 할 UX 이슈를 정리했어요.

특히 이해도와 이용 의향은 높았지만, 피드백과 조작 효율은 상대적으로 낮다는 차이를 확인하면서, 제품팀이 기능 자체보다 사용 흐름 개선에 집중해야 한다는 방향을 제안할 수 있었습니다.

최종적으로는 Interaction, UX Writing, IA 개선 방향을 포함한 Product Recommendation으로 정리해 다음 제품 개선 논의에 활용할 수 있는 기준을 만들었습니다.

# What I Learned

## 좋은 검증은 문제를 찾고, 무엇부터 고칠지 결정하게 만드는 과정

프로젝트를 진행하면서 사용성 평가는 단순히 ‘사용자가 무얼 좋아하는지’를 확인하는 과정이 아니라는 걸 배웠습니다.

중요한 것은 단순히 긍정/부정 반응을 모으는 것이 아니라, 사용자가 어디서 멈추고 왜 혼란을 느끼는지 확인한 뒤 제품팀이 바로 실행할 수 있는 우선순위로 바꾸는 것이었어요.

특히 접근성 제품에서는 작은 문구, 피드백 속도, 메뉴 구조 하나가 사용 가능 여부를 결정할 수 있다는 점을 경험했습니다.

이후로 기능을 평가할 때 항상 ‘이 기능이 좋은가’보다 ‘사용자가 스스로 이해하고 통제할 수 있는가’를 먼저 보게 되었습니다.
